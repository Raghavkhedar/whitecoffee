## Architecture

**Next.js 14 static export** → Firebase Hosting. `output: 'export'` in `next.config.ts`; `next start` unused — builds produce static HTML in `/out`. All pages are `'use client'`.

**Data flow**: Pages → `src/lib/firestore.ts` → Firebase SDK. All Firestore operations are centralized in `firestore.ts` (40+ functions). Pages use local `useState` — no global state.

**Auth guard & tab access**: `src/app/(admin)/layout.tsx` listens to `onAuthStateChanged`, redirects to `/login`, and admits a user via `hasPortalAccess` — `role === 'admin'` (superuser, all tabs) **or** a non-empty `tabAccess` array on their `users` doc (scoped access). Access is **fully granular per-tab**: `tabAccess: string[]` holds the exact tab *paths* an employee may use (e.g. `['/attendance','/ot-shortage']`) — the old preset-`tags`/`TAG_TABS` bundle system is **retired**. The layout also runs a central per-tab URL guard (`canAccess`) that redirects to the user's `landingPath` if they reach a tab they lack, so hand-typed URLs are blocked without per-page code. Access logic is pure/unit-tested in **`src/lib/portalAccess.ts`** (the single tab registry the Sidebar renders from, an `adminOnly` flag on `TabDef`, and `allowedPaths`/`canAccess`/`landingPath`); the layout provides the user via `AccessContext` (`useAccess`). **Admin-only tabs** (`adminOnly: true` → never grantable, never a matrix column): `/dashboard`, `/users`, `/access`, `/daily-activity`, `/audit`. The other 10 tabs are grantable. `/audit` is admin-only *because the rules are* — `audit_log` reads are admin-gated since entries carry full document snapshots including pay; granting the tab to a manager would render an empty page. `portalAccess.test.ts` asserts the admin-only list so it cannot drift from `firestore.rules`. Admins assign access two ways, both writing `tabAccess`: the **admin-only `/access`** page — a bulk employees×tabs checkbox matrix — and per-tab checkboxes in the `/users` edit modal. Firestore rules enforce the same model **collection-first**: `userTabs()` reads `tabAccess`, and per-domain helpers (`canReadAttendance`, `canAccessLeaves`, `canWriteOtApprovals`, …) unlock each collection only for the tab(s) that use it; user-management writes stay admin-only (no self-promotion). **Add a grantable tab** = a `TABS` entry + map its collections to the right helper(s) in `firebase/firestore.rules` (both the per-doc `match` and the top-level `{path=**}` collection-group `match`). Rules deploy: `firebase deploy --only firestore:rules` **from the repo root** (the Firebase MCP deploy tool runs from the wrong cwd and silently deploys nothing — always verify with `firebase_get_security_rules` after).

**Routing**: `(admin)` is a route group (no URL segment) — `/dashboard`, `/access` (admin-only access matrix), `/working-hours-shortage-excess`, `/users`, `/leaves`, `/regularization`, `/attendance`, `/daily-activity` (admin-only same-day punch correction), `/ot-shortage`, `/ot-settlements`, `/manpower-utilisation-input`, `/submissions`, `/conveyance`, `/notifications`, `/audit` (admin-only audit trail) are all protected.

## Firestore Collections

- `audit_log/{autoId}` — **tamper-proof before/after record of every write**, written ONLY by the `auditTopLevel` / `auditUserSubcollection` Cloud Function triggers (Admin SDK). `allow write: if false` for everyone including admin — an audit log a suspect can edit is not evidence. Admin-only read. Each entry: `path`/`collection`/`docId`/`userId`/`changeType`/`changedKeys`/`before`/`after`/`actor`/`atMillis`. `fcmToken` and `activeSessionToken` values are redacted; **pay is not** — "who changed a salary from what to what" is the point. `actor` comes from the document's own `lastModifiedBy` (stamped by both clients on every write), falling back to `approvedBy`/`markedBy`/etc., else `"unknown"` — triggers carry no auth context, so there is no other source, and **no IP is available anywhere** (rules have no `request.ip`). Surfaced at `/audit`. ⚠️ `audit_log` is excluded from auditing in `functions/auditLog.js` or the trigger recurses without bound.
- `users/{uid}/compensation/current` — **pay, split off the user doc**: `salaryRate`/`pfPercent`/`esiPercent`/`imprestPercent`. Firestore rules are DOCUMENT-level, so while pay sat on `users/{uid}` any tab that read a user doc to resolve a name could read every salary. Read: admin + `/ot-settlements`. Write: admin. The employee is deliberately NOT granted read on their own pay. Resolve via `lib/compensation.ts` `withPay()` (mirrored in `functions/compensation.js`), which falls back **per field** to the legacy inline value — a whole-document fallback would blank PF/ESI on a partially written doc, and `0` is a real value, not "absent".
- `users/` — employee profiles; `role`: `admin` | `office` | `operations` | `sales`. **`sales` is a hybrid** (office-style fixed window + ops-style hybrid check-ins and conveyance, no OT/shortage/WO/categories/manpower). Almost every role decision used to be a binary `isOps = role === 'operations' ? … : …`, which drops `sales` into the office branch silently — route role decisions through **`src/lib/roleCapabilities.ts`** (mirrored in `firebase/functions/roleCapabilities.js` + Android `RoleCapabilities.kt`; keep all three in lockstep). Design: **`docs/superpowers/specs/2026-07-16-sales-role-design.md`**. Optional **`level`** (`'Level 1'`..`'Level 20'` or `null`) is an admin-set band on the user doc, edited in the `/users` add/edit modal (dropdown built from the `LEVELS` array); **recorded only** — no function, export, or rule reads it.
- `sites/` — site records with GPS coordinates. **There is no geofencing** — coordinates are stored and shown, but nothing validates a punch against them (the server-side check was removed for exactly this reason). Readable by every signed-in user because the app needs the site list to check in.
- `users/{uid}/leave_requests/` — employee-submitted leave (the app creates it; the portal only ever approves/declines/cancels). Two **overlay** fields narrow what a leave grants, and neither ever rewrites `fromDate`/`toDate`/`totalDays` — those stay the record of what was ASKED for: `approvedDates[]` (what the approver granted) and `cancelledDates[]` (granted days an admin later revoked, with `cancelledBy`/`cancelComment`/`lastCancelledAt`). ⚠️ **Their empty cases are INVERTED and that asymmetry is load-bearing**: empty/absent `approvedDates` = the WHOLE range is granted (so every legacy doc keeps its meaning, no backfill), empty/absent `cancelledDates` = NOTHING cancelled. Reading either the other way silently unpays real leave. Effective leave = granted − cancelled; `status` stays `approved` throughout (there is no `partially_approved` or `cancelled` status — every `status === 'approved'` reader in three languages would have to learn about it, and a missed one turns a granted day into an Absent). The rule lives in **`firebase/functions/leaveCoverage.js`** (`leaveCoversDate`/`explicitGrantedDates`/`grantedDayCount`, `npm test`) and is mirrored by `admin/src/lib/leaveDates.ts` + Android `LeaveRequest.kt` — **change all three together**. Design: `docs/superpowers/specs/2026-07-20-partial-leave-approval-design.md` + `docs/superpowers/specs/2026-08-05-leave-cancellation-design.md`.
- `users/{uid}/attendance/` — check-in/out events. Ops `site_in`/`site_out` carry free-text `siteName`; `siteId` is filled later by admin via **Manpower Utilisation Input** page (`updateAttendanceSiteId`). Events are otherwise immutable, except an **admin** may **delete** trailing punches for the current day via the **Daily Activity** page (same-day accidental-checkout fix — see below); every deletion is snapshotted into `attendance_corrections/`.
- `users/{uid}/attendance_corrections/{autoId}` — immutable audit log of admin same-day punch corrections (Daily Activity page). Each doc snapshots the deleted punches verbatim (`removedEvents[]`) plus `date`/`reason`/`correctedBy`/`correctedByUid`/`correctedAt`/`keptEventId`. Written by `restoreAttendanceToEvent`; admin-only create+read, never updated/deleted.
- `users/{uid}/attendance_status/{date}` — computed daily status (written by `computeDailyAttendanceStatus`). Statuses: `Present`/`HalfDay`/`SL`/`LNF`/`Absent`/`SCHL`/`USCHL`/`WO`, plus the rest-day statuses `Sunday`/`Holiday`. **`SCHL`** (Scheduled Leave) is the nightly function's status for a day inside an approved leave with no punches (written nightly for today, or by `scoreRetroactiveLeave` for days that had already passed when the leave was approved) — always the string `SCHL`, with a per-day **`salaryCredit: 1 | 0`** field carrying whether it was paid (1 = drew a day from `plBalance`, 0 = balance already exhausted; pure resolver `resolveLeaveStatus` in `attendanceRules.js`). **`Holiday`** docs carry a `salaryCredit` too (`resolveHolidayCredit` in `holidayCredit.js`): `0` for an operations employee who worked that holiday, `1` for everyone else; a legacy Holiday doc with no field is paid. **`USCHL`** (Unscheduled Leave) is **never** written by the nightly function — admin-only, set as a Regularization outcome; always unpaid, no `salaryCredit` (regularizing any day, and a `cancelLeave` revert to `Absent`, deletes a previous auto doc's `salaryCredit`). **`PL`/`LWP`** are **legacy**: retired for new writes; existing docs stay (and stay visible, and the readers keep handling them) until the migration script `firebase/functions/scripts/migrateLegacyLeaveStatuses.js` has been run, after which none remain (see "Legacy `PL`/`LWP` migration" below). **WO** (paid no-work day off for ops) is admin-set (`markedBy:'admin'`) via the Attendance page (Mark WO / clear) or as a regularization outcome; the WO day itself pays 1×rate unconditionally, and its standard-8h debit is recorded in the `wo_ledger` collection (not in the monthly OT/shortage net), settled by explicit admin action or written off after 2 months. Optional `inTime`/`outTime` (`"HH:MM"`) = **effective worked window** captured when an admin regularizes a day **to Present** (missed-punch fix); when present, the OT/shortage ledger uses these **instead of raw events** for that date, so a corrected Present day carries shortage/OT (set via `approveRegularization`; non-Present outcomes clear them)
- `users/{uid}/planned_hours/{date}` — admin-set shift window for ops (`startTime`/`endTime` as `"HH:MM"`); office fixed 10–18. ⚠️ **A shift saved for a PAST date never re-scores that day** — the nightly run only ever writes *today*, so the doc is stored and silently ignored (observed for real: a `planned_hours/2026-07-09` created on 07-10 changed nothing). Harmless for a standard shift now that no-plan days default to 10:00–18:00, but a **non-standard** one (e.g. 12:00–20:00) fails to apply. `savePlanned` on the Attendance page therefore shows a dismissable amber warning after saving any past-dated shift, pointing at Regularization instead. It **warns, it does not block** — the admin may still want the roster on record. Optional `declaredOtMins` = admin pre-declared overtime for that day (OT worked up to this is auto-approved; set inline on the Attendance page next to the shift). The legacy `otAuthorized` field is **retired** by the OT redesign (Protocol 1): nothing reads or writes it any more (it survives only as a `@deprecated` optional in the TS type so old docs deserialize), and there is no "Authorize OT" toggle — all Sunday/holiday work becomes pending OT for admin approval (see **Rest-day OT** under Shortage & Overtime)
- `users/{uid}/daily_hours/{date}` — per-day `plannedMins`/`actualMins`/`shortageMins`/`otMins` (written by `computeDailyAttendanceStatus`, fully-worked days only)
- `users/{uid}/ot_approvals/{date}` — admin OT decision: `requestedMins`/`approvedMins`/`status` (`approved`|`rejected`)/`manual`/`reason`/`approvedBy` (written by `approveOt`/`rejectOt`/`setManualOt`). `manual:true` = admin-entered OT for a day with no auto-detected surplus (e.g. missed-punch anomaly), added via the **Add manual OT** form in the OT/Shortage drill-in modal; counted as granted OT in the ledger like any approval
- `users/{uid}/settlements/{YYYY-MM}` — frozen monthly OT/shortage/WO settlement (one per ops employee): full breakdown + `netMins` + `settlementCash` + `locked`/`settledBy`. Written by admin **Settle & Lock** on the **OT Settlements** page (`settleMonth`); the Cloud Function reads the **previous month's locked** settlement and adds `settlementCash` to payroll TOTAL DUE (OT paid in arrears). `settlementCash = woDays×rate + netMins/480×rate`
- `users/{uid}/material_requests/`
- Top-level: `material_purchases`, `material_transfers`, `tool_transfers`, `work_progress`, `conveyance`
- `holidays/{date}` — company-wide holidays (`title`/`description`), marked by admin on the **Attendance** calendar. A marked day is never scored Absent: the nightly function writes a `Holiday` status doc for every active user with no doc yet (a Sunday gets a payroll-neutral `Sunday` doc the same way), and `Holiday` credits **+1 day** in Days NP (non-Sunday only — a Sunday-dated Holiday still gets its doc but adds 0, since the month-to-date Days-NP loop skips Sundays first). **Exception:** an operations employee who actually worked the holiday (complete in/out pair, worked minutes > 0) gets `salaryCredit: 0` on their Holiday doc — no +1, because all rest-day work is raised as pending OT and that approval is their pay for the day; everyone else gets `salaryCredit: 1`, and a legacy doc with no field is paid. It is excluded from expected working days and from expected-hours/shortage math (a paid day off, nothing more). The +1 is ALSO withdrawn at pay time when approved OT exists for that date (e.g. manual OT granted for a missed-punch holiday, which the nightly saw as nothing to approve and left at `salaryCredit: 1`) — readers apply `effectiveHolidayCredit` (`holidayCredit.js`), so the credit frozen at 23:59 from punches is reconciled with the approval and the day is never paid +1 and OT together. Managed via `setHoliday`/`deleteHoliday`, which both refuse any date before today (IST) — a past day is already scored, so it is fixed through Regularization (`admin/src/lib/holidayGuard.ts`); the refusal is a CLIENT-SIDE admin guard only — `firestore.rules` still permits a direct write; read by `getHolidaysForMonth`/`getHolidaysForDateRange`.

Required composite indexes (Firebase Console):
- `leave_requests`: `status` ASC + `submittedAt` ASC
- `attendance`: `date` ASC + `timestamp` ASC
- `material_requests`: `submittedAt` DESC
- collection-group `planned_hours`: `date` ASC (for `getPlannedHoursForMonth`, `getPlannedHoursForDateRange`)
- collection-group `attendance`: `date` ASC + `timestamp` ASC (for `getAttendanceForDateRange`)

## Attendance Status Logic

> Full backend reference: **`docs/cloud-functions.md`** (all 6 functions, triggers, collections, deploy/auth notes).

`computeDailyAttendanceStatus` Cloud Function runs at 23:59 IST. **Sundays and company-wide holidays (`holidays/{date}`) are not scored: the function writes a `Sunday` / `Holiday` status doc (`resolveRestDayType` in `attendanceRules.js`; Holiday wins when both apply) for every active user who has no doc yet — an existing auto/admin doc wins — then returns. No penalty; `Sunday` credits 0, `Holiday` credits +1 day (a Holiday dated on a Sunday adds 0 — the month-to-date Days-NP loop skips Sundays first). A Holiday doc carries `salaryCredit`: `0` for an operations employee who worked it (complete in/out, worked minutes > 0 — paid through OT approval instead), `1` for everyone else; a legacy doc with no field is paid.**

**Events and window by role** (event types + window come from `roleCapabilities`, not a hardcoded branch):
- **Office/admin**: `office_in` / `office_out`; fixed 10:00–18:00 IST
- **Operations**: first in / last out across both site and market visits (`site_in`/`market_in` and `site_out`/`market_out`); window from `planned_hours/{date}`. **No plan but they worked → scored against the default 10:00–18:00** (matching `otLedger.ts`'s `DEFAULT_SHIFT_START_MIN`/`DEFAULT_SHIFT_END_MIN`). **No plan + no approved leave + no work events → Absent**, exactly like office. Approved leave still produces SCHL. ⚠️ **Flipped 2026-07-17** — ops used to be scored only on plan OR leave OR punches (the since-deleted `shouldEvaluateDay`), so a blank day was "unscheduled" and cost nothing. Now **every ops working day must be marked**: a plan for working days, WO or leave for days off. A forgotten entry is **−2 days NP**, not a silent no-op. Sundays and `holidays/{date}` (rest-day docs, early return), offboarded users (`active === false`) and admin-marked days are still not scored — those guards are function-level, upstream of the per-user loop.
- **Sales**: hybrid — first in / last out across **all** of `office_in`/`site_in`/`market_in` → `office_out`/`site_out`/`market_out`, scored against the **fixed 10:00–18:00** window (never a `planned_hours` shift, so no plan is ever needed). Same status buckets. **No** `daily_hours`/`ot_approvals` are written — sales has no OT/shortage/WO concept.

| Status | Condition | Salary (days) |
|--------|-----------|---------------|
| Present | In by window start AND out after window end | 1 |
| Short Leave (SL) | Both punches present, early-out only (checked in on time, no late-in) — any amount, zero grace | 0.75 |
| Half Day | Any late-in at all, however small — zero grace; wins over an early-out on the same day | 0.5 |
| LNF (Log Not Found) | Exactly one punch (missing check-in OR check-out); formerly SLNF | 0.5 |
| SCHL (Scheduled Leave) | Day inside an APPROVED leave, no punches. Always `SCHL`; `salaryCredit` says whether it was paid | 1 if `salaryCredit: 1` (drew from `plBalance`), 0 if `salaryCredit: 0` (balance exhausted) |
| USCHL (Unscheduled Leave) | **Admin-only** — Regularization outcome; never written by the nightly function. No `salaryCredit`, no conveyance, creates no wo_ledger debt (and clears any stale one — `approveRegularization` deletes a non-WO date's ledger doc). Regularizing an auto-SCHL day to USCHL clears its `salaryCredit` (`approveRegularization` deletes the field, as `cancelLeave`'s revert to Absent does); payroll would ignore a stray one anyway because only `status === 'SCHL'` counts credit | 0 |
| Holiday | `holidays/{date}` — auto-written for every active user (no punches needed) | 1 (non-Sunday; 0 if the Holiday falls on a Sunday; 0 if `salaryCredit: 0` — an operations employee who worked it, paid via OT approval instead; also 0 for an ops employee with approved OT that date, reconciled at read time by `effectiveHolidayCredit`; a legacy doc with no `salaryCredit` is paid) |
| Absent | No events, no approved leave — all roles alike (ops included, since 2026-07-17) | -2 |

Legacy `PL` (= paid, 1) / `LWP` (= unpaid, 0) docs written before the SCHL change stay in Firestore, and stay visible, until the migration script below has been run (the TS `AttendanceStatus` type keeps them as legacy members; badges/counts handle them). `SCHL` example: 4 approved leave days with `plBalance` 2 → all four read `SCHL`, the first two `salaryCredit: 1`, the last two `salaryCredit: 0`.

**Legacy `PL`/`LWP` migration (supersedes the earlier "no migration" decision).** `firebase/functions/scripts/migrateLegacyLeaveStatuses.js` is a local, dry-run-by-default, backed-up and reversible script that relabels those docs (`PL`→`SCHL` credit 1, admin `LWP`→`USCHL`, other `LWP`→`SCHL` credit 0; pay-neutral); run steps are in `docs/superpowers/specs/2026-09-19-legacy-leave-status-migration-design.md`. **Until it has been run against production and a re-run confirms 0 remaining AND its status histogram shows no unrecognised statuses (`REMAINING: 0` cannot see near-misses like `"pl"`/`"PL "`), all legacy `PL`/`LWP` handling above stays.** Once confirmed, that handling (the `PL`/`LWP` cases in `tallyAttendanceStatus`/`dayWeight`/`cancelLeave`, the TS legacy members and badges) can be deleted in a separate change.

`markedBy: 'auto'` on function-written docs; `markedBy: 'admin'` docs (regularization) are skipped on recompute. The attendance page mirrors this logic client-side until the nightly run writes it (`deriveStatus`, a 4th copy of the rule — keep it in lockstep with `attendanceRules.js`).

**Which date the nightly scores, and how a failed run shows up.** `computeDailyAttendanceStatus` scores the **scheduled** date — taken from the event's `scheduleTime` (`functions/nightlyClock.js`), not the wall clock — so a scheduler retry that lands after IST midnight repairs the date that failed instead of scoring the next one (before this, a failed 23:59 run left its date entirely unscored and scored D+1 prematurely). A `scheduleTime` more than 48 h old or more than 1 h ahead is refused (throws, nothing scored) rather than trusted; a missing/unparseable one falls back to the wall clock (`clockSource: "wall-clock"` on the doc). `functions/nightlyGuard.js` writes a **`started` marker** (`startedAt`, `clockSource`, `scheduleTime`) to `system/nightly_runs/computeDailyAttendanceStatus/{date}` before scoring, so a run that never finished is a doc **without `ranAt`** rather than no doc at all; a run that throws leaves `ok: false` + `error` + `failedAt` on that doc and re-throws so the scheduler retries. A later successful run replaces the doc wholesale (its summary carries `startedAt`/`clockSource` too), so no stale `error`/`failedAt` survives. Sunday/holiday runs return early and write the marker but no summary, so **a rest-day doc legitimately has no `ranAt`**. ⚠️ The code only *records* this — nothing alerts on it. Wiring a real alert (a Cloud Monitoring log-based alert on the `computeDailyAttendanceStatus: … FAILED` `console.error` lines, and/or a check for a working-day doc missing `ranAt` or carrying `ok: false`) is an **operator task**, not something the deployed function does.

**`markedBy: 'backfill'` — 22 docs, 2026-07-09..16, 5 ops employees (S106/S271/S276/S353/S369), written 2026-07-17.** One-time recovery of ops days that were *worked* but never scored, because the pre-2026-07-17 function skipped any ops day with no `planned_hours`. Scored by the same rule the nightly now uses (plan if present, else default 10:00–18:00). **Punches-only** — no Absent/PL/LWP was ever created retroactively, so the backfill could only add days people worked, never remove pay; days with no punches were left unmarked. Existing docs (incl. admin regularizations) were never overwritten. The HTTP function was deployed, dry-run, committed, then deleted — it is not in source, matching the earlier `backfillAttendanceStatus` precedent. Note some recovered days had a plan entered *late* (e.g. a `planned_hours/2026-07-09` created on 07-10), after that night's run had already skipped them: **entering a shift retroactively does not re-score the day** — the nightly only ever writes today. A second pass then scanned **all 22 users, every role, inactive included**, and found exactly **one** further recoverable day (a suspended test account, deliberately left) — confirming the bug only ever touched operations, that office/admin/sales were never affected, and that the recovery is complete.

**Days NP** (pure, unit-tested `computeDaysNP` in `functions/payrollDeductions.js`): `present + SL×0.75 + halfDay×0.5 + LNF×0.5 + Σ(salaryCredit over SCHL days) + holiday×1 − absent×2` (`holiday` counts non-Sunday Holiday docs whose `salaryCredit` is not 0 — the MTD loop skips Sundays — after `effectiveHolidayCredit` has also zeroed it for an ops employee with approved OT that date). Only the **paid** slice of SCHL counts; USCHL and unpaid SCHL contribute 0. In the current-month Sheets block, legacy `PL` folds into SCHL-paid and legacy `LWP` into SCHL-unpaid so a mid-month deploy loses no credit (this fold only matters until the legacy docs are migrated to `SCHL`/`USCHL`; after migration none remain). ⚠️ The Days-NP weights are mirrored in three places that must change together: `computeDaysNP` + `tallyAttendanceStatus` (`functions/payrollDeductions.js`, used by the Sheets MTD block) and `STATUS_WEIGHT`/`dayWeight` in `functions/dailySpend.js` (Daily Spend Snapshot / Forecast).

**Salary**: `daysNP × salaryRate`

PL balance (`plBalance`, label unchanged): +1 on 1st of month (`accrueMonthlyLeave`), -1 per **paid SCHL day** (`salaryCredit: 1`) drawn by the nightly run (or by `scoreRetroactiveLeave` for past days of a late-approved leave); USCHL and unpaid SCHL never decrement it.

## Google Sheets Export

`exportToSheets` Cloud Function runs 16:30 UTC (22:00 IST) → Google Sheet (`SHEET_ID` in `functions/index.js`) via service account (`ATTENDANCE_SHEETS_KEY` secret).

- **Always resolve Name/ID from the live `users` collection** — not the snapshot values on each doc. Use `uidOf(doc)` + `userNameMap`/`userEmpIdMap` (keyed by uid). `uidOf` reads `userId` field, falling back to parent path for subcollection docs.
- **Attendance tab** is per-employee/day (not per-event): In Time / In Location / In Site ID / Out Time / Out Location / Out Site ID / All Activity / OT (mins) / Daily Status / PL Balance / WO Balance. Built from union of attendance events and status docs — Absent/SCHL/USCHL/LNF (and legacy PL/LWP) days appear even without check-in events. **All Activity** = full chronological log with resolved Site ID in brackets. **OT (mins)** = per-day *credited* OT matching the Employee Dashboard, computed by a port of `otLedger.ts`'s `computeDayLedger` (declared auto-approved + authorized rest-day + admin-granted incl. manual; pending/unauthorized excluded); keep the port in sync with the TS source. **PL Balance** = each employee's current `plBalance` (repeated per row). **WO Balance** = each employee's current `woBalance` (repeated per row). ⚠️ **Nothing in the codebase writes `woBalance`** — it is only ever read (Working Hours page, Users export, this tab), so the column shows `0` for everyone until some backend actually populates the field. **Blank data cells are filled with `θ`** (header row untouched; a real `0` PL/WO balance stays `0`).
- **Employee Dashboard tab** — MTD summary, one row per employee: Date | EMP Name | EMP ID | Level | Days Passed | Present | SL | Half Day | LNF | SCHL (Paid) (×1) | SCHL (Unpaid) (×0) | USCHL (×0) | Holiday (×1) | Absent | Leaves | Days NP | Salary Rate | Salary Due MTD | Covy Due | Imprest Due MTD | OT/WO amount | PF (−) | ESI (−) | TOTAL DUE. **Leaves** = all SCHL + USCHL days (incl. legacy PL/LWP folded in, as above); Days NP uses `computeDaysNP`. Frozen past-month blocks keep their old `PL (×1)` / `LWP (×0)` column layout — each block is self-describing. Includes CF BAL (carry-forward leave) and TOTAL summary rows. **Level** = each employee's `user.level` (recorded-only band, blank if unset); like the OT/WO header rename, **frozen past-month blocks keep their old column layout without Level** — only the current block carries it (each block is self-describing). **PF / ESI / Imprest are computed percentages of Salary Due MTD** (`daysNP × salaryRate`), so they grow through the month like salary does — the pure, unit-tested **`functions/payrollDeductions.js`** (`npm test`): `PF = base × user.pfPercent%`, `ESI = base × user.esiPercent%`, `Imprest = base × user.imprestPercent% × efficiency`. **PF and ESI are DEDUCTED** from TOTAL DUE; Imprest is added. The **deduction base is floored at 0** — Absent is −2 days NP so Salary Due MTD can go negative, and a percentage of a negative base would *add* money back. ⚠️ **`efficiency` defaults to 1, NEVER 0** — the efficiency matrix doesn't exist yet and no caller passes it; a 0 default would silently pay everyone ₹0 imprest. Conveyance is built from the `conveyance` collection (**operations + sales** — gated by `usesConveyance(role)`, so a new conveyance-earning role needs only a table row). Sales appears on this tab with salary + conveyance and a 0 OT/WO amount (non-ledger role). **OT/WO amount** (renamed from `Settlement`, 2026-07-18) = each ops employee's **WO-day pay plus net authorized OT** for the **current** month, in rupees (`woDays×rate + netMins/480×rate`): every WO day ADDS 1×rate unconditionally, while `netMins` = authorized OT (auto + granted, net of minutes settled onto WOs) − shortage — the WO's 480-min debit lives in `wo_ledger` and does not participate in `netMins` — signed (±). It is computed **live every nightly run** straight from the ledger — **no longer gated on Settle & Lock**, so it grows through the month and can read **negative** mid-month (shortage before OT accrues). Only **authorized** OT counts (auto-approved within declared + authorized rest-day + admin-granted); **pending and unauthorized-rest-day OT are excluded**. Because it is built from the same authorized numbers the OT Settlements page locks, it **equals that month's `settlementCash` by construction** — just shown earlier. Computed by the pure, unit-tested **`functions/otAggregate.js`** + **`functions/otLedger.js`** (`npm test`), fed month-scoped events/planned/approvals/statuses/holidays; non-ledger roles (office/admin/sales) → 0. ⚠️ **Frozen past-month blocks keep their old verbatim `Settlement YYYY-MM (₹)` header** — only the current block uses the new `OT/WO amount (₹)` header, so the column heading differs across blocks (harmless; each block is self-describing). **TOTAL DUE** = salaryDue + covy + imprest + otWoAmount **− PF − ESI** — so **TOTAL DUE now also moves live** through the month with authorized OT (was flat at the locked value before). **The tab now keeps month history**: instead of overwriting a single snapshot, each nightly run preserves every past month's block **verbatim (frozen)** and rebuilds only the **current** month's block, stacked **current-on-top** in the same tab. Blocks are delimited by a banner row `── MONTH: YYYY-MM — Month Year ──` (parsed via `/MONTH:\s*(\d{4}-\d{2})/`); each block carries its own header + CF BAL + TOTAL. A month freezes automatically once the IST calendar rolls over. ⚠️ **The computed Imprest REPLACED the manual Sheet column (2026-07-17)** — `imprestFromBlock` was deleted and nothing reads the typed-in value back. Since **no user has `imprestPercent` set yet, the column reads ₹0 for everyone**; that is decided and expected, not a bug, and stays ₹0 until the percentages are populated on `/users`. Frozen past blocks keep their own manual imprest. Frozen = never recomputed — a later fix to a past month does not change that month's block. Parse/freeze/merge/order logic is the pure, unit-tested `functions/dashboardHistory.js` (`npm test`); first-run migration wraps the old single-block tab into the correct month.
- **Overtime Exception Report tab** — written to its **own** spreadsheet (`SHEET_ID_OT` in `functions/index.js`), **operations only** (`usesOtShortageLedger(role)` — sales excluded), **current month, cleared & rebuilt each run**. ## Working Hours-Shortage/Excess Page

`/working-hours-shortage-excess` (`src/app/(admin)/working-hours-shortage-excess/page.tsx`) — real-time view of expected vs actual working hours across a configurable date range.

- **Filters**: date preset (Today / Last 7/15/30/90/180/365 days / custom), role, individual employee
- **Columns**: Name, Emp ID, Role, PL, WO, Working (expected), Actual, Shortage, Overtime
- **Single-day view**: also shows Check-in / Check-out times
- **Expected hours**: office/admin/sales = 8 h × working days (Mon–Sat); ops = sum of admin-set `planned_hours` windows
- **Sales**: appears here, but **Shortage/Overtime render `NA`** — its fixed window scores status only. Gated by `tracksShortage(role)` (true for office/admin/ops, false for sales); it is a **separate axis** from `usesOtShortageLedger` because office/admin show shortage while running no ledger. Sales is **excluded entirely** from OT & Shortage, OT Settlements, and Manpower Utilisation Input.
- **Actual hours**: derived from `office_in`/`office_out` (office) or `site_in`/`market_in` … `site_out`/`market_out` (ops) attendance events
- **Data**: `getAttendanceForDateRange` + `getPlannedHoursForDateRange` + `getOtApprovalsForDateRange` (all `collectionGroup`)
- Sundays excluded from working day count; sort order: office → admin → ops → sales, then alphabetical

### Shortage & Overtime (per-day, every minute counts)

Computed **per worked day** (both check-in and check-out present — absent/leave/LNF days never count). The shift window is the ops `planned_hours` window for that date; **ops days with no plan fall back to the default 10:00–18:00** (`DEFAULT_SHIFT_*_MIN`); office/admin is always fixed 10:00–18:00. ⚠️ **An inverted/mis-entered window (end before start, e.g. end `06:00` meaning 6pm) does NOT fall back here** — `computeDayLedger` gates on `if (shiftEndMin > shiftStartMin)` and otherwise returns `ZERO`, so such a day silently accrues **no shortage and no OT**. That is a deliberate divergence from the status rule, where `resolveOpsWindow` (functions / app / `lib/attendanceRules.ts`) falls back to 10:00–18:00 — so one mis-entered shift is scored for attendance but ignored by the ledger. Revisit if that asymmetry ever bites. **Late-out pays off late-in before any OT is credited** (changed 2026-08-22, superseding the earlier independent-edge rule): staying past shift end first makes up the minutes missed by arriving late, so only the **surplus** beyond break-even is OT and only the **remainder** of the lateness is shortage. A normal day is therefore **never both at once** — in 11:00 / out 18:30 on a 10–18 shift is 30 shortage and 0 OT, not the "30 OT + 60 shortage" the old rule produced. **Early-out is NOT part of that netting and can never be cancelled** (a day cannot end both before and after shift end, so an early-out day has no late-out to offset it); arriving early still pays for nothing. **Arriving early NEVER earns OT** — the only source of OT on a normal day is staying past shift end *beyond* covering any lateness:
- **Shortage** = `max(0, checkIn − shiftStart)` (late-in) `+ max(0, shiftEnd − checkOut)` (early-out). Automatic, no approval. Computed live for the selected range; the nightly function writes the canonical per-day `daily_hours/{date}`. (The old lifetime `users/{uid}.shortageMins`/`approvedOtMins` counters are **retired** — no longer written or read; OT/shortage net per-month via the ledger.)
- **Overtime** = `max(0, checkOut − shiftEnd)` (late-out only; early check-in is ignored), split by the day's `declaredOtMins` (pre-declared by admin): worked OT **up to `declaredOtMins` is auto-approved** (no review); only the **surplus beyond it is pending** and needs admin action. The dashboard lists pending OT days; admin grants an adjusted amount (≤ the beyond-declared surplus) with a **mandatory reason** via `approveOt`, which writes `ot_approvals/{date}`. Admin can also **reject** a pending OT day (`rejectOt`, reason required → `ot_approvals` with `status:'rejected'`), or **manually grant OT** for a day the system can't auto-detect (`setManualOt` → `manual:true` decision; e.g. missed-punch anomalies). Declared OT is a pre-approval **ceiling, not an obligation** on the OT earned — it never changes shortage, and leaving before the declared end never creates extra shortage (shortage is measured against the plain shift). The core math is `computeDayLedger` in `src/lib/otLedger.ts` (edge-based, takes shift start/end + actual in/out as IST minutes-of-day). `savePlanned` on the Attendance page rejects `endTime ≤ startTime`.

**Rest-day OT**: ops work on a Sunday/holiday — and on an admin-marked **WO** date — is **all-hours PENDING OT** (`pendingExtraMins`) for the whole worked window, for an admin to approve or adjust in the OT approval flow. It is **never auto-credited**, raises **no shortage**, and the declared-OT ceiling (`declaredOtMins`) does **not** apply. There is no pre-authorization: the earlier `planned_hours.otAuthorized` gate (Protocol 1 of the OT redesign removed it) no longer exists, so an employee who turns up unasked creates a *request*, not a liability — nothing is paid until an admin approves it. (Because that approval is the pay for the day, an operations employee who works a company holiday also has the Holiday's +1 withdrawn — see `holidays/{date}`.) **WO** days pay a full day **unconditionally** (`woDays×rate` in `settlementCash`). Each WO also carries a 480-minute (`WO_DEBIT_MINS`) debit, tracked in the `users/{uid}/wo_ledger/{date}` collection (**Protocol 3**) and **not** netted into the monthly `netMins`: it is cleared only by an explicit admin settlement (`settleWoDebit` redirects minutes of approved OT onto it, recorded as `settledMins` on that OT day) or, unsettled after 2 months, written off by the `expireWoDebits` nightly function with zero pay impact. So one WO with no OT that month still pays its day.

**Regularized days**: approving a regularization **to Present** with effective `inTime`/`outTime` (on the `attendance_status` doc) makes that day carry shortage/OT — the ledger uses the override **instead of raw events** for the date (authoritative). Lets a missed-punch day count correctly.

**Monthly netting & payroll** (replaces the old "tracked separately, never netted"): approved OT (auto + granted, net of minutes settled onto WOs) minus shortage **net within a month** to `netMins` (WO debits do **not** participate — they live in `wo_ledger`); admin **Settle & Locks** the month on the **OT Settlements** page → `settlementCash = woDays×rate + netMins/480×rate` → the Cloud Function adds the previous month's locked `settlementCash` to payroll **TOTAL DUE** (OT paid in arrears). The per-day/range math lives in **`src/lib/otLedger.ts`** + **`src/lib/otAggregate.ts`** (pure, unit-tested via `npx tsx src/lib/*.test.ts`), shared by the OT/Shortage page, Working Hours-Shortage/Excess page, and OT Settlements page. Full spec + decisions: **`docs/ot-shortage-design.md`**. Cloud Function changes need **`firebase deploy --only functions`**.

## Daily Activity Page (admin-only)

`/daily-activity` (`src/app/(admin)/daily-activity/page.tsx`) — same-day fix for an employee who checked out by mistake. The Android app derives live check-in/out state purely from the **last** punch (`deriveAttendanceState`), so "undo" = remove the erroneous **trailing** punches; ending a day from a site is two punches (`site_out` then `home_out`), so restoring "at site" removes both.

- **View**: pick a date (defaults to IST today), each employee with activity = a card with their chronological punch **timeline** + current derived state. Role + employee filters. Data via `getAttendanceForDate`.
- **Edit (today only)**: each punch shows **"Restore to here"** = keep this punch, delete everything after it. Confirm dialog previews the punches to remove + resulting state (via `deriveState`) and requires a **mandatory reason**. Past days are read-only (past-day fixes stay with Regularization).
- **Action**: `restoreAttendanceToEvent(uid, date, keepEventId, reason, adminName, adminUid)` — one atomic batch that re-reads the day's events (guards against a stale client list), hard-deletes the trailing punches, and writes a full snapshot to `attendance_corrections/`. Nothing is lost; the live timeline stays clean for the phone, nightly compute, OT ledger, and Sheets.
- **History**: each employee card shows a **Corrections** section listing every correction on the selected date (removed punches + who/why/when), fetched via `getAttendanceCorrectionsForDate` (collectionGroup scan on `attendance_corrections`, admin-only). Visible on past days too.
- **State-derivation port**: `src/lib/attendanceState.ts` (`deriveState`/`eventLabel`) is a pure port of the Kotlin `deriveAttendanceState` — **keep in sync with the Android source**. Unit-tested via `npx tsx src/lib/attendanceState.test.ts`.
- **Rules**: admin-only `delete` on `attendance` events + admin-only create/read on immutable `attendance_corrections` (`firebase/firestore.rules`). Design: **`docs/superpowers/specs/2026-07-14-daily-activity-punch-correction-design.md`**.

## Leaves Page

`/leaves` (`src/app/(admin)/leaves/page.tsx`) — the approval queue. Employees apply from the **Android app only**; there is no create path in the portal (rules: `allow create: if isOwner(userId) && status == 'pending'`).

- **Approve** opens a per-date checkbox picker over `requestedDates`, **all ticked** (approving everything stays two clicks). Unticking grants a subset → `approvedDates`. Sundays/holidays in the range are flagged (they are never leave days). A **partial** approval notifies the employee; a full one stays silent.
- **Cancel leave** (admin-only, added 2026-08-05) is the undo an approval never had: a per-date picker over the **still-granted** days, **nothing ticked by default** (a pre-ticked list is one stray Enter away from revoking a whole holiday), a **mandatory** reason, and a "Past" flag on days already scored. Writes `cancelledDates`; always notifies. `cancelLeave` re-derives what is still granted from the **server** copy, so a stale tab cannot double-cancel.
  - **Already-scored days are reversed** to `Absent` — a leave-scored day (`SCHL`, or legacy `PL`/`LWP`) has zero punches by construction, so with the leave gone it is exactly the nightly scorer's own `no leave → Absent` fallback. Future days need **no** attendance write at all: `leaveCoversDate` simply stops covering them.
  - ⚠️ The revert is gated on `markedBy === 'auto'`, upholding the same invariant the nightly function does — **an admin-marked day is never silently rewritten**. A day independently regularized after the leave scored it keeps that later decision; the date is still recorded as cancelled and returned in `skippedDates` for an amber note.
  - ⚠️ **Only a day that actually drew from `plBalance` refunds it:** paid SCHL (`salaryCredit === 1`) or a legacy `PL` day. Legacy `LWP` and `SCHL` with `salaryCredit` 0/missing (leave taken with a zero balance) never decremented anything, so refunding them would mint leave from nothing. This is the **only `plBalance` increment in the codebase** outside `accrueMonthlyLeave`'s monthly +1.
  - **Admin-only on purpose**, unlike approve/decline which any `/leaves` manager may do: reverting a scored day writes `attendance_status` (needs `/attendance` or `/regularization`) and the `plBalance` refund writes the user doc (**admin-only in the rules**), so a manager's cancellation would be denied the moment it touched a past day. The button is gated on `useAccess().user.role === 'admin'` rather than failing after the form is filled in.
  - Re-cancelling is a safe no-op: the revert wrote `markedBy: 'admin'`, so the guard rejects it and no second refund can happen.
- **Leave approved AFTER its days have passed** is scored by the `scoreRetroactiveLeave` Cloud Function (`firebase/functions/retroLeaveScoring.js`, pure planner + unit tests; `retroLeaveRunner.js` holds the trigger body — the transaction, early exits and logging — and `npm run test:emulator` in `firebase/functions` exercises it against the Firestore emulator): every granted past day whose status is an auto-written `Absent` becomes `SCHL` (paid/unpaid by the running `plBalance`, which is decremented in the same transaction, exactly as the nightly run would have decided). Days with punches, admin-marked days, `Sunday`/`Holiday` docs and days with no doc are untouched; cancelled and ungranted dates are skipped; re-running it is a no-op. It is a Cloud Function, not portal code, because `plBalance` writes are admin-only in the rules and status writes are tab-gated. Needs `firebase deploy --only functions`.
- **Needed no Firestore rules changes** — `leave_requests` update, `attendance_status` write, and `users` update already admit admin. The 110-test `firebase/rules-tests` suite is the regression gate.
